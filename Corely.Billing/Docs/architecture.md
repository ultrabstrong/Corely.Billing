# Architecture

Layered the same way as [Corely.IAM](https://github.com/ultrabstrong/Corely.IAM): public services over internal processors over repositories.

```
Services (public) → Processors (internal) → Repositories/UoW → BillingDbContext → Database
```

## Layers

| Layer | Visibility | Responsibility |
|-------|-----------|----------------|
| Services | `public` | The host's API; the only layer a host can decorate |
| Processors | `internal` | Validation, grant selection, the ledger |
| Repositories | `internal` | [`Corely.DataAccess`](https://github.com/ultrabstrong/Corely.DataAccess) repositories and unit of work |
| `BillingDbContext` | `internal` | One context for `Grants`, `GrantRequests` and `ConsumptionEvents` |

## Processors

| Processor | Owns |
|-----------|------|
| `GrantProcessor` | Grant CRUD and the live-grant query |
| `GrantRequestProcessor` | Requests, and approving one into a grant in one unit of work |
| `ConsumptionProcessor` | Writing holds, settling and releasing them, idempotency |
| `ConsumptionReportProcessor` | Every ledger read, and the rule for what counts |
| `QuotaProcessor` | Splitting quantities across grants, settlement arithmetic, overdraft |

`QuotaProcessor` works out settlement in terms of grants and hands the ledger a per-grant split. The ledger never infers anything about grants.

## Domain Structure

```
Domain/
├── Enums/            # Enums that are not result codes
├── Entities/         # EF Core entities and their configurations
├── Models/           # Request, result and domain models
├── Processors/       # Business logic + telemetry decorators
├── Mappers/          # Entity ↔ model mapping
└── Validators/       # FluentValidation rules
```

Domains: `Grants`, `GrantRequests`, `Registrations`, `Consumption`, `Quota`.

## Schema

| Table | Key | Indexes |
|-------|-----|---------|
| `Grants` | `GrantId` | `AccountId` |
| `GrantRequests` | `GrantRequestId` | `(AccountId, Status)` |
| `ConsumptionEvents` | `ConsumptionId` | unique `(AccountId, IdempotencyKey)`, `(AccountId, CorrelationId)` |

Operations and units are stored as their tokens. Tags are stored as JSON. Ids are version 7 GUIDs generated by the library, so they sort by creation on every provider.

## Notes

- No foreign key joins the tables; deleting a grant never touches the ledger or the request that asked for it
- Migrations live in the provider projects and ship in the CLI; the library never migrates at runtime
- History is kept in `__CorelyBillingMigrationsHistory`
